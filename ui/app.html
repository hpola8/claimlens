Connecting

The AI drafts in pencil. A person signs in ink.

ClaimLens reads an insurance claim, finds the policy clauses that apply, and drafts a decision that cites them. Each draft is checked for invented facts, then waits for a reviewer. Nothing reaches a customer until someone approves it.

You're viewing the demo. Sample claims replay responses recorded from the Spring AI backend, and your own claims get keyword matching only. Run the Spring Boot app with an OpenAI key for live drafts.

  1. Step 1

    Screen the claim

    Claim text is untrusted. Look for hidden instructions aimed at the AI.

  2. Step 2

    Find policy clauses

    Vector search over the policy, limited to this claim's policy type.

  3. Step 3

    Draft a decision

    The model may use only those clauses and must cite each one it relies on.

  4. Step 4

    Check for made-up facts

    Citations are verified, then a second model checks the draft against the clauses.

  5. Step 5

    Send to a reviewer

    Clean drafts get one-click approval. Anything flagged gets a full review.

How it works

A Spring Boot service built on Spring AI. Each step in the pipeline maps to a specific piece of the framework or a guardrail written for this project.

Pipeline

  1. IngestPolicy markdown is split on clause headings, so every chunk carries exactly one clause ID. Chunks are embedded and written to a Spring AI VectorStore (SimpleVectorStore by default, PGVector with the pgvector profile).
  2. ScreenInjectionDetector flags instruction-like phrases in the claim text. The system prompt also marks claim text as data only.
  3. RetrieveSearchRequest with topK and a metadata filter on policyType. Clauses under the similarity cutoff are dropped; if none remain, the assistant abstains.
  4. DraftChatClient with a versioned system prompt and structured output: .entity(ClaimDecision.class) returns a typed Java record.
  5. VerifyCitationValidator rejects any clause ID the model wasn't shown. Spring AI's RelevancyEvaluator and FactCheckingEvaluator judge the draft against the evidence.
  6. RouteRoutingPolicy sends denials, low confidence, high value and any failed check to full review. All drafts enter the queue.
  7. ReviewA person accepts, edits or rejects. Overrides are logged as evaluation data, and the audit log records every step.

Known limitations

  • Model confidence is self-reported and not calibrated. It is one routing signal among several, never the only one.
  • The injection screen is pattern-based and can be evaded. It raises the review level; it doesn't make injected text safe.
  • The judge model can share blind spots with the drafting model. Reviewer overrides are the ground truth.
  • Retrieval works clause by clause, so clauses that refer to each other (like mold coverage depending on water coverage) need both to be retrieved.
  • Sample policies are simplified and do not reflect any real insurer's terms.
